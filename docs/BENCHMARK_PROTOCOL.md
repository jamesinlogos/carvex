# CarveX benchmark protocol (protocol-v1)

> **Status:** frozen at git tag `protocol-v1` on 2026-11-19. The tag commit and
> this file's SHA-256 are recorded in `docs/PROGRESS.md`. This file is not
> modified after the first lockbox results; execution evidence goes into
> `docs/VALIDATION.md`.
>
> All figures currently published in `README.md`, `docs/REPORT.md`, and
> `bench/results/final/` belong to version 0.1.0's **dev-set D1**, not to
> lockbox results. The lockbox-v1 run uses new seeds 1001–1020 but the same
> D1-style synthetic profile; D2–D7 remain OPEN.

## 1. Research questions

- **RQ1 — Structural validator:** does structure checking (header/footer + parser +
  score threshold) reduce false positives compared to pure header/footer carving
  without reducing recall on the same file set?
- **RQ2 — FS-aware:** when separated from algorithm quality, how much do restricting
  the search to unallocated space and aligning to cluster boundaries contribute to
  precision/recall and time? This question *cannot* be answered using all-deleted
  images alone, where whole-image and unallocated are nearly identical.
- **RQ3 — Performance vs. size:** how do time, throughput, and peak RSS change from
  64 MiB to 8 GiB at 1/2/4/8 threads?
- **RQ4 — Degradation from fragmentation/overwrite:** how do recall and `splice_rate`
  change when 10/30/50% of files are fragmented into 2–4 fragments and when
  10/30/60% of clusters are overwritten?
- **RQ5 — Metadata:** what does metadata-based recovery (`undelete`/`hybrid`) add
  (names, timestamps, runlist) over pure carving, and does it increase junk-FPs?

## 2. Hypotheses

| ID | Hypothesis | Test |
|---|---|---|
| H1 | Validator reduces the main FPs (junk+spliced) with negligible recall loss on intact files | Per-file McNemar + bootstrap |
| H2 | On mixed images, unallocated increases precision vs. raw; on all-deleted images, the two modes are equivalent | Paired comparison by file |
| H3 | Time increases nearly linearly with image size at the same data density; throughput does not drop >20% from 64 MiB → 8 GiB | Regression + CI |
| H4 | Fragmentation/overwrite monotonically decreases recall; `--salvage` increases byte_recall but does not increase junk-FP beyond CI | Dose–response curve |
| H5 | Metadata recovery increases recall for fragmented files and provides exact names/timestamps; junk-FPs do not increase | Compared with truth per record |

## 3. Metrics

### 3.1. File-level

- **exact:** the output's SHA-256 equals the source file's SHA-256.
- **usable:** SHA-256 after trimming the tail after the last valid footer (JPEG EOI,
  PNG IEND, PDF `%%EOF`) — for tools that append NUL/newline.
- **viewable:** the output can be opened/verified by an independent tool (Pillow
  `verify()` + `load()`; PDF via `qpdf --check` or `pypdf` + `pdftoppm`).
- **partial:** `byte_recall ≥ τ` (default τ = 0.5) even if not exact.
- **precision/recall/F1** are computed on unique files; every ratio includes Wilson 95%.

### 3.2. Block-level

- `byte_recall` = correct bytes / source bytes.
- `byte_precision` = correct bytes / output bytes.
- `splice_rate` = bytes belonging to another file / output bytes.

### 3.3. False positive classification

Separate: `junk`, `spliced`, `duplicate`, `kept_allocated`, `embedded`.
**Main FP = junk + spliced + duplicate.** Report two views:
*deleted-only* and *any-real-file*.

### 3.4. Performance

- wall-clock, user+sys CPU, peak RSS, bytes read (`/proc/<pid>/io`).
- ≥10 repetitions; cold cache (`posix_fadvise DONTNEED` or drop caches) and warm.
- 1/2/4/8 threads (`taskset`), 64 MiB → 8 GiB curve.
- Record CPU, RAM, kernel, I/O scheduler, governor.

Rules:

- Ground truth is generated by the builder independently of CarveX; hashes and
  fragment lists (LBA, length) are recorded before deletion.
- Dev seeds 1–20 are used for tuning. Lockbox seeds 1001–1020 are run once only
  and are not used to fix code.
- No files with duplicate hashes between dev and lockbox.
- The builder asserts the actual fragmentation/overwrite levels itself.

**Current D1 status:** 30 files repeated across 4 images; each file appears in both
FAT32 and NTFS, all-deleted and mixed. Therefore "100 files" is **100 scoring
instances**, not 100 unique files. Every report must state `n_files_unique = 30`,
`n_images = 4`.

| Tool | Version | Configuration | Notes |
|---|---|---|---|

| Sleuth Kit | available (`tsk_recover`, `blkls`, `fls`) | Not used in the published numbers | Metadata baseline planned |

**Known limitations (F-16, F-19):** the current number tables run Foremost/Scalpel/
PhotoRec on the **whole image**, while CarveX runs unallocated on free space. This
is not a same-search-space comparison. The future protocol requires every tool to
run both: (a) whole-image, (b) the unallocated blob extracted with `blkls`. The
configurations must be locked before lockbox results are viewed.

## 6. Statistics

- Unit of analysis: **unique file**, not duplicated across images.
- Wilson 95% CI for every ratio.
- Paired comparisons: exact McNemar and/or paired bootstrap ≥10,000 times, sampled
  by file; Holm correction for multiple comparisons; report effect size.
- Performance: median, IQR, min/max; do not conclude "faster" if CIs overlap.

**Current status:** `bench/run_benchmark.py` only reports TP/FP/FN,
precision/recall/F1 and average time; Wilson/McNemar/bootstrap are **not**
implemented. No inferential statistics have been published.

## 7. Dev/lockbox workflow

1. Complete the protocol + metrics + runner (C-01…C-07).
2. Create commit and tag `protocol-v1` before any lockbox output is viewed.
3. Run dev seeds 1–20, adjust code if needed.
4. Freeze the code; run lockbox seeds 1001–1020 **once**.
5. Store immutable results + `SHA256SUMS`; do not modify code based on results.
6. If a real bug is found: fix it, generate a new lockbox seed, disclose that the
   old lockbox was used.

**Lockbox-v1 design (fixed before the tag):**

- 20 new corpora, seeds 1001–1020, generated by the unchanged D1 corpus builder.
- Five seeds each: all-deleted/FAT32, all-deleted/NTFS, mixed/FAT32, mixed/NTFS.
- 64 MiB images, one repetition per tool, all five tool/mode specs
  (CarveX-unallocated, CarveX-raw, Foremost, Scalpel, PhotoRec).
- Every generated file hash is checked against the dev corpus and against earlier
  lockbox seeds; any collision aborts dataset construction.
- Runner command line, configs, metrics and carving code remain unchanged. The
  historical `--partition largest --no-gaps` pin stays in force.
- Result directories are new and never overwrite `bench/results/final` or
  `bench/results/baseline-v0.1`.

**Status at freeze:** step 1 is incomplete (D2–D7, block metrics, statistics,
ablation missing); steps 4–6 **not run**. There are no lockbox results.

## 8. Planned ablations

- Validator off (signature only) vs on.
- Nested suppression on/off.
- `--align none` vs `auto/cluster/sector`.
- Score threshold 0…100 (PR curve).
- `--validate decode` on/off (cost and precision).
- `--repair` on/off.
- Salvage on/off (when a flag exists).

## 9. Threats to validity

### Internal

- D1 is synthetic, with files repeated across 4 images; 100% results are not
  representative of real data.
- 64 MiB images, FAT32 512 B clusters, disk ~22% full, no fragmentation/overwrite.
- Timing measured on warm cache, 3 repetitions; no CI.
- The corpus is generated by the project itself; it may inadvertently be "easy"
  for CarveX.

### External

- No real Windows/NTFS images, exFAT, E01, block devices.
- Only simple baseline/progressive JPEG, 8-bit PNG, PDF 1.4 xref table.
- No encrypted PDFs, xref streams, ObjStm, JPEG DRI.

### Construct

- `exact` by SHA-256 is too strict for truncated files; `usable` is too lenient.
- No block-level metrics or FP classification yet, so "FP" currently merges
  kept/embedded.
- `n=100` is scoring instances, not unique files.

### Conclusion

- All "100%" claims apply only to D1 and the exact/usable measures.
- Do not generalize to real disk images, fragmented data, or unsupported formats.
